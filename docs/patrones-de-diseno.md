# Registro de patrones de diseño

El enunciado exige patrones **aplicados y justificados**. Cada vez que se implementa uno, se agrega aquí una fila (la skill `/aplicar-patron` lo hace sola). Esta tabla es la base para la defensa del proyecto.

## Aplicados

| Patrón | Categoría | Servicio | Archivo(s) | Problema que resuelve | Por qué este y no otro |
|---|---|---|---|---|---|
| Factory Method | Creacional | identity | `identity/domain/user.py` (`User.register`) | Crear un usuario válido exige generar el UUID, rechazar `ADMIN` y registrar `UserRegistered`; un constructor libre permitiría saltarse esas reglas | Un Builder no aporta: los campos son pocos y todos obligatorios |
| Smart/Dumb Components | Frontend | frontend | `frontend/src/features/auth/containers/*Page.tsx` (smart), `features/auth/components/*Form.tsx` (dumb) | Que un formulario no mezcle la llamada a la API, la sesión y la navegación con el render; así el form se prueba y reutiliza solo | Un componente por pantalla con todo adentro es el "componente Dios" que pide evitar `frontend/CLAUDE.md` |
| Facade | Estructural | frontend | `frontend/src/features/auth/useAuthActions.ts` (`useLogin`, `useRegister`), `features/catalog/useCatalog.ts`, `features/property-detail/usePropertyDetail.ts`, `features/agent/properties-admin/useAgentProperties.ts` | Las páginas necesitan "ingresar" o "registrarse" con su estado (enviando, error), sin conocer `authApi`, React Query ni el manejo de tokens | Llamar a `authApi` desde la página acopla la UI a la API y repite el manejo de errores en cada pantalla |
| Repository | DDD | identity | `identity/domain/repository.py`, `identity/infrastructure/persistence/repositories.py` | El dominio no debe conocer el ORM de Django | Usar `UserModel` directo en el handler acoplaría el caso de uso a Django y exigiría una base en cada test |
| Adapter | Estructural | identity | `identity/infrastructure/security/password_hasher.py` | Adaptar los hashers de Django al puerto `PasswordHasher` de la capa de aplicación | Llamar a `make_password` desde el handler metería a Django en `application` |
| Adapter | Estructural | identity | `identity/infrastructure/security/token_issuer.py` | Adaptar PyJWT al puerto `TokenIssuer`: la aplicación pide tokens sin saber cómo se firman | Usar `djangorestframework-simplejwt` no sirve: no pone `kid` en el header |
| Outbox | Integración | identity | `identity/infrastructure/persistence/repositories.py`, `identity/infrastructure/messaging/relay.py` | Guardar el usuario y publicar en Kafka son dos sistemas: si uno falla, quedaría un usuario sin evento o un evento sin usuario | Publicar directo en el handler pierde el evento si Kafka está caído; una transacción distribuida no existe entre PostgreSQL y Kafka |
| Command | Comportamiento | identity | `identity/application/commands/register_user.py` | Encapsular la intención de registrar un usuario, separada de HTTP (CQRS) | Sin `CommandBus` (Mediator): con pocos casos de uso, el handler se invoca directo desde la vista (KISS) |
| Factory Method | Creacional | listing | `domain/model/Property.java` (`Property.create`) | Una propiedad debe nacer en `DRAFT`, con id generado por el dominio, título, precio y zona válidos, y registrar `PropertyCreated`; con un constructor público se podría crear en cualquier estado | Un Builder sobra: los datos obligatorios son pocos; los opcionales (características, imágenes) entran después por métodos con sus propias reglas |
| Service Registry + Self-Registration | Microservicios | listing | `application.properties` (`spring.cloud.consul.*`), `infrastructure/config/ConsulReregistration.java` | Las réplicas de listing (`--scale listing-service=3`) cambian de IP; el gateway necesita saber cuáles están vivas | Registrar a mano en el compose no sigue a `--scale`; el re-registro cada 60 s cubre los reinicios de Consul en modo dev |
| Repository | DDD | listing | `domain/repository/PropertyRepository.java`, `FavoriteRepository.java`, `infrastructure/persistence/JpaPropertyRepository.java` (+ `PropertyMapper`) | El aggregate `Property` debe guardarse y cargarse entero (imágenes y características) sin que el dominio conozca JPA | Usar las `*JpaEntity` como modelo de dominio metería anotaciones de Hibernate en `domain` y mezclaría reglas con mapeo |
| Command | Comportamiento | listing | `application/command/*Command.java` + `*Handler.java`, `PropertyCommandSupport` | Cada intención del agente (publicar, pausar, reservar...) es un objeto con su handler, separado de HTTP y reutilizable por la política | Sin `CommandBus` (Mediator): los handlers se inyectan directo en el controlador (KISS); `PropertyCommandSupport` evita repetir cargar, verificar dueño, guardar, proyectar y publicar |
| CQRS | Arquitectura | listing | `infrastructure/persistence/JdbcCatalogProjection.java` (escribe), `JdbcCatalogReadModel.java` (lee), tabla `property_catalog` | Buscar con filtros sobre el aggregate obligaría a cargar imágenes y características de cada propiedad; el catálogo es público y se lee mucho más de lo que se escribe | Una proyección en la misma transacción es consistente al instante; alimentarla por Kafka agregaría consistencia eventual sin necesidad dentro de un mismo servicio |
| Builder | Creacional | listing | `application/query/CatalogCriteria.java` | El catálogo tiene 8 filtros opcionales, paginación y orden; un constructor con 10 parámetros nulos es ilegible | Un `Map` de filtros pierde los tipos y la validación (precio mínimo ≤ máximo, campos de orden permitidos) |
| Specification | DDD | listing | `infrastructure/persistence/CatalogSqlSpecifications.java`, `SqlFilter.java` | Cada filtro del catálogo se traduce a una condición SQL que se combina con AND solo si el filtro viene | Concatenar SQL con `if` en el read model mezcla todos los filtros en un método largo y difícil de probar |
| Adapter | Estructural | listing | `application/port/ImageStorage.java`, `infrastructure/storage/LocalImageStorage.java` | La galería se guarda en disco hoy, pero mañana podría ir a MinIO o S3 sin tocar los casos de uso | Escribir archivos desde el handler ataría la aplicación al sistema de archivos y complicaría los tests |
| Outbox | Integración | listing | `infrastructure/messaging/OutboxEventPublisher.java`, `OutboxRelay.java` | Guardar la propiedad y publicar en Kafka son dos sistemas: si uno falla, visit tendría una copia desactualizada | Publicar en el handler pierde el evento si Kafka está caído. `FOR UPDATE SKIP LOCKED` permite varias réplicas sin publicar lo mismo a la vez |
| Event-driven policy | Integración | listing | `application/policy/ReserveOnLeadWonPolicy.java`, `infrastructure/messaging/LeadEventsConsumer.java` | Cuando visit cierra una oportunidad como ganada, la propiedad debe reservarse sin que visit llame a listing por HTTP (ADR 0005) | Una llamada HTTP acoplaría la disponibilidad de los dos servicios; si la regla no se cumple se registra un `WARN` y no va a la DLQ, porque no es un error técnico |
| Anti-corruption layer | DDD | listing | `infrastructure/messaging/LeadEventTranslator.java`, `application/policy/LeadClosed.java` | El modelo de visit (`Lead`, su envelope) no debe filtrarse al dominio de listing | Leer el JSON de visit dentro de la política acoplaría listing al formato de otro servicio y a sus cambios de versión |
| Mapper (traductor de eventos) | Integración | listing | `infrastructure/messaging/PropertyIntegrationEventMapper.java` | Los eventos de dominio son internos; los de integración son contratos públicos (`contracts/events/listing/`) | Serializar los eventos de dominio tal cual rompería a visit con cualquier refactor del aggregate |
| Chain of Responsibility | Comportamiento | gateway | `gateway/internal/middleware/middleware.go` (`Chain`), `gateway/cmd/gateway/main.go` | Cada request debe pasar por varios controles (recover, correlation-id, logs, identidad…) y cualquiera puede cortarla, sin que el proxy los conozca | Una función gigante con todos los controles acopla todo y no se puede probar eslabón por eslabón. Es también un Decorator de `http.Handler`; lo que la hace cadena es que un eslabón puede cortar |
| Service Registry (cliente) | Microservicios | gateway | `gateway/internal/discovery/discovery.go` | Las réplicas nacen y mueren con IP distinta: el gateway no puede tener direcciones fijas. Consulta en Consul las sanas y guarda un snapshot, así una request nunca espera a Consul | El DNS de Docker Compose resuelve nombres, pero no tiene health checks ni registro explícito (ADR 0002) |
| Strategy | Comportamiento | gateway | `gateway/internal/balancer/balancer.go` (`Strategy`), `round_robin.go` | Hoy se reparte con round robin, pero otro algoritmo (menos conexiones) no debería obligar a tocar el proxy ni el Circuit Breaker | Un `switch` por algoritmo dentro del balanceador crece con cada caso y mezcla el reparto con el marcado de réplicas |
| Circuit Breaker | Resiliencia | gateway | `gateway/internal/balancer/balancer.go` (`MarkDown`, `Pick`) | El health check de Consul tarda hasta 10 s en notar una réplica caída: mientras tanto, parte de las requests fallaría | Reintentar en otra réplica podría duplicar un `POST`. Un breaker por servicio apagaría también las réplicas sanas |
| Proxy | Estructural | gateway | `gateway/internal/proxy/proxy.go` | Hay que interponerse entre el cliente y la réplica para elegirla, limitar el body y traducir los errores de transporte, sin que el cliente lo note | Un redirect expondría las direcciones internas y dejaría al cliente hablar directo con el servicio |
| API Gateway | Microservicios | gateway | `gateway/cmd/gateway/main.go` | El cliente no debe conocer cuántos servicios hay ni dónde están, y auth, CORS y rate limit no deben repetirse en cada uno | Spring Cloud Gateway o KrakenD resuelven casi todo por configuración: quedaría poco diseño propio que defender (ADR 0002) |
| Factory Method | Creacional | notification | `internal/domain/notification.go` (`NewNotification`) | Un aviso debe nacer con UUID del dominio, destinatario válido y el texto fijo de su tipo; un constructor libre permitiría saltarse esas reglas | `Reconstitute` queda aparte: cargar un aviso guardado no debe validar ni generar identidad |
| Repository | DDD | notification | `internal/domain/notification.go` (`NotificationRepository`) | El aggregate no debe conocer SQL | Usar pgx en los handlers acoplaría los casos de uso a la base y exigiría una base en cada test |
| Event-driven policy | Integración | notification | `internal/application/policies.go` (`EventPolicies`) | Decidir a quién avisar ante cada evento, sin que esa regla conozca el formato del mensaje de Kafka | Ponerla en el consumidor mezclaría una regla de negocio con infraestructura |
| Anti-corruption layer | DDD | notification | `internal/infrastructure/kafka/consumer.go` (`handlerFor`) | Los eventos de otros servicios no deben filtrarse al modelo de avisos; de `UserRegistered`, además, no se debe leer el email ni el nombre | Importar sus modelos acoplaría los servicios y traería datos personales que nadie usa |
| Observer / Pub-Sub | Comportamiento | notification | `internal/infrastructure/kafka/consumer.go` | Avisar ante cambios de otros servicios sin que ellos sepan que este existe | Que visit o listing llamen por HTTP acoplaría a los productores y rompería la regla de oro 2 |
